# 比特交替协议

rdt3.0 协议，简单说下到此为止的可靠数据传输协议推导 —— 自顶而下给出了一个非常不错的推导，核心思想即先假设不会出问题，得到最简的状态机，然后针对每一个步骤可能出现的问题（比如包损坏，丢包等）进行解决，拓展有限状态机

有意思的例子 —— “人在口述报文的时候，没说出一点，就等待接收方的反馈，比如 ’ 对对对 ‘ ，‘ 等等，你刚说了什么？‘ ” 类似这样，这就是停等协议的直观描述。

在 2.1 的情况下使用了 ACK 和 NAK 的机制，那么 2.2 直接使用序号传输以规避了 ANK 的使用，感觉其实语义也会清晰一些，即每一次回复的时候都是 “唔，我保证成功收到的是xx报文”，而不是分成两个不同的状态“我成功收到报文”，“请你重传报文”

假设 Sender 向 Receiver 发送了 Package 0，那么 Receiver 成功接收之后回复 ACK 0；接着 Sender 继续发送 Package 1，残念， 包损坏，于是 Receiver 目前依旧保证成功的还是 ACK 0，所以就回复 Sender ACK 0；那么 Sender 连续收到了两次 ACK 0，即接收到了冗余 ACK 后，知道对面没有正确的接收到 Package 1，所以触发重传

上述不能解决丢包问题，如果 Package 直接没送到 Receiver 手中，那么也无法触发重传等恢复机制。所以引入计时器，如果在计时结束之后依旧没有收到回复报文，则直接重传当前包

但是停等协议会使得性能限制非常大，那么对应方法即引入流水线 —— 允许发送方发送多个分组且不需要等待回复。

那么我的理解就是一个缓冲区的事情，允许发送批数据，然后利用滑动窗口在缓冲区内进行 Check / 通知回退，也是非常经典的玩法
