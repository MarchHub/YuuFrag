# 程序执行

首先，大前提是机器上的 CPU 有且仅能执行机器码，所以实际上不管通过什么路子，最终都必须要得到机器码交付运行

## AOT（Ahead of Time）

非常直接的思想，离线的编译过程之后，最终由链接器交付的可执行文件就是原生机器码，即所有的翻译工作全部在执行前完成。

比如常见的 C/C++，以及 Rust 之类的

优势非常明显，在 Runtime 没有其他的翻译开销，冷启动非常快；不过缺陷也同样明显 —— 编译之后就是 Native Code 了，所以比如想要在运行期进行代码生成等这种比较“动态”的能力就比较弱

## 虚拟机

那么另一种方案，即我们先把源码翻译成一种平台无关的中间表示（IR / 字节码），然后在执行的时候启用对应平台的虚拟机将这个字节码进行翻译成机器码执行

- 解释器（Interpreter），**逐条**读取并分派字节码指令，通过预先实现的机器码逻辑执行对应指令的语义
- JIT Compiler，本质 Compiler，将**一段**字节码转成对应的 Native Code，供 CPU 直接执行

简单来说，解释器一行一行走，最粗糙的实现类似一个巨大的 `while-true` + `switch-case`，所以对于很多跨指令的优化就难以实现

那么再看 JIT，它确乎可以进行局部构建，不过注意，这是在 Runtime 的时候进行的转译成机器码，所以假设源码多，那么其启动效率就比较低（可以理解为需要先预热）

### JVM

非常经典的，Java / Kotlin 走的 JVM 路线 —— JVM 接收字节码并执行，但是内部却有一个解释器和 JIT Compiler 混合执行

既要又要是这样的 —— 在启动期，规避了将所有源码全部交付给 JIT 进行翻译的延迟；在运行期，可以统计一些数据，然后将部分字节码进行优化 —— 比如某段代码被反复执行，就可以利用 JIT 编译成 Native Code，加速之后的运行

### CLR

C# 正常的执行链路也非常相似，但是在编译期的时候会生成 CIL（通用中间语言）与类型元数据打包成程序集，在运行期交付给 CLR 运行

那么在 Runtime 的时候，传统的 CLR 会在第一次碰到方法的时候调用 JIT 进行编译，不过如果启动瞬间还是碰到了大量的冷方法，等其“变热”依旧是一个很卡顿的事情。

所以现代做法有点类似 JVM —— 首次调用的时候先不做耗时优化，在之后经由热点统计觉得需要优化了再重新调用 JIT 进行优化

以及在编译的时候打包的元数据 —— Runtime 天生具备非常强的反射能力和代码自省能力，以及 CLR 上的 JIT 也可以借助这些元数据执行优化魔法

### “真”解释

类似 Python / Lua，它们常被成为 “解释性语言”，原因也非常直接 —— 其在 Runtime 的时候基本上就是字节码经由解释器循环执行实现

比如 CPython，就是 Python 源码文件经过分析成字节码之后来进行执行的运行时环境

那么它慢的原因就显而易见 —— 没有一个成熟的 JIT，所以 CPU 跑的永远只是那个解释器本身，那么业务代码难以进行跨指令的黑魔法优化；而且 Python 中的类型都是动态类型，所有的 Object 都需要在运行期进行类型检查，指针运算，引用计数等很多烦琐的事情（不过其实也一直在被优化，比如 CPython 3.11+ 的自适应字节码特化、PyPy、V8 与 LuaJIT 之类的，主要思路也是引入特化的解释器或者 JIT）
