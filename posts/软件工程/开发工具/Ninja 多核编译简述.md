# Ninja 多核编译简述

简单说下 `Ninja` 进行多核编译调度的原理

不过首先值得注意的, Ninja 本身并不会进行预处理, 语法分析等, 它只相当于一个“指挥官”, 组织这些事情如何按照一定的顺序进行

## DAG

首先, 编译过程是有”依赖“的, 比如要编译 main 的产物, 那么可能需要先编译 `module A` 和 `module B`, 所以此时 main app 就依赖 `module A` 和 `module B`. 那么实际上可以非常容易想到使用一个有向图来进行这种关系的表达

在 Ninja 当中, 它以文件为点, 指令为边, 构建整个 DAG, 接着就可以非常方便简单的利用拓扑排序来找到某种可行的编译顺序, 得到最终的编译流程, 然后交付执行

这可以, 但还不够优雅 —— 它不能解决在多线程的条件下高效的进行调度

## 加权

那么让权重高的线路先进行编译, 权重低的放在后面进行编译 —— 重要的先行, 不重要的放缓. 也是常见的 trick, 那么在 Ninja 中, 它以 “编译时间” 作为权重进行赋权

先来解释下为什么这样是合理的 —— 首先我们的优化目标是 “编译总时间” 最短, 那么这个 $T$ 的下届很容易确定, 即最耗时的关键路径的编译时间. 所以假设在我们现在拥有多个核心的情况下, 如果把这条关键路径留到最后执行, 那么其仅只能占用一个核心, 导致其他核心只能干等. 这显然不是我们想要的, 显然的, 所有核心空等的时间越短越好.

那么其实优化的思路已经出来了 —— 优先让最耗时的任务占用一个核心允许, 然后让其他任务再吃掉空闲核心, 这样在自然语言的描述当中, 非常有最优解的感觉

当然, 在调度理论中, 最小化 Makespan 是一个 NP-Hard 问题, 所以使用启发式算法来进行优化.

好的, 现在假设有两个核心和三个可以并行的任务, A 需要消耗 10s, B 需要消耗 10s, C 需要消耗 1s. 使用贪心的策略先执行 A, B. 但是十分极端的, 假设之后有一个依赖 C 的任务 D, 耗时是 10年, 那么在执行完 A, B 之后, 有一个核心需要空等十年!!

上述反例说明, 仅仅贪心的考虑当前最耗时任务存在漏洞 —— 我们需要考虑一整条关键路径上的权重. 那么考虑沿边求和呢?

依旧不是很妙 —— 比如 A -> B; A -> C; 也就是假设在 A 完成之后解锁 B 和 C 两个可以并行的独立任务, 但是在 `sum` 的世界中, 其实一切都是串行的, 即反向传播到 A 点的时候, 其总消耗时间成为了 `T(A) + T(B) + T(C)` 而不是 `T(A) + max(T(B), T(C))`, 再考虑一下, 

诶等等, 似乎刚已经说明了应当如何传播 —— 即

$$
W(u) = w(u) + max(W(v))
$$
其中 $W(v)$ 表示所有从 u 的直接后继节点

不赖, 现在拥有了反向传播权重的公式, 那么提前计算之后, 再做一次“在线”的拓扑排序, 把每次入度为零的点压入大根堆中; 如果还有空闲槽位即消费堆顶元素

以及其获取“编译时间”的方式也比较有趣 —— 权重来自 `.ninja_log` 记录的**上一次构建的实际耗时**；如果是首次冷构建（无历史记录），真实任务默认权重为 `1`（退化为按依赖链跳数/深度优先），`phony` 伪目标权重为 `0`。
